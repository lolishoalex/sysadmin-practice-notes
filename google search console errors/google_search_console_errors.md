# Task 11 — Помилки Google Search Console: діагностика та планування

**Тип об'єкта (навчальний кейс):** багатомовний новинний сайт на WordPress
(мультимовний плагін, CDN/проксі перед origin, VPS-хостинг, нещодавня міграція
сервера, попередній інцидент із диском).

**Мета практикуму:** навчитися читати звіти GSC, відрізняти реальні проблеми від
шуму й вирішити, що виправляти зараз, а що — на етапі перебудови сайту.

---

## Стек і інструменти, з якими працювали

| Область | Інструменти / технології |
|---|---|
| Пошукова аналітика | Google Search Console (звіти «Індексування», «Досвід → AMP», структуровані дані), експорт даних, Rich Results Test, validator.schema.org |
| Структуровані дані | Schema.org: `Event`, `VideoObject`, `NewsArticle`, `WebPage`; плагіни-генератори схеми, SEO-плагін, AMP |
| WordPress | плагіни (CLI-інвентаризація), CPT і permalink-структура, WPML-мультимовність, `robots.txt`, `noindex`, плагін безпеки |
| Веб-сервер / мережа | nginx, 301-редиректи на regex, HTTP-коди (200/301/403/404/5xx), soft 404, канонічні теги, CDN-проксі та SSL-режими |
| CLI-діагностика | `curl -sI` + `grep` для читання заголовків, `wp-cli` (`plugin list`), `grep -rl` для пошуку джерела розмітки |
| Методологія | зіставлення листів-нотифікацій із живими графіками, аналіз трендів у часі, кореляція сплесків з інфраструктурними подіями, класифікація URL за патернами |

---

## Що пройдено на практиці

1. **Читання звітів GSC.** Різниця між листом-нотифікацією (фіксує дату
   *виявлення*, не зникає сама) і графіком активних елементів, який показує
   поточний стан. Робоче правило: реагувати лише там, де активна цифра ≠ 0.

2. **Домен vs сервер.** З'ясовано, що новий сервер не обнуляє помилки GSC:
   індексується домен, а помилки рівня застосунку (схема, редиректи, 404,
   robots) переносяться разом із сайтом.

3. **Класифікація помилок по кошиках** — структуровані дані, AMP, минулі
   інфраструктурні сплески, індексування сторінок. Для кожного визначали:
   критичність, джерело, чи лікується переїздом, коли виправляти.

4. **Пошук джерела розмітки.** Через `grep` по каталогах плагінів визначено,
   який саме плагін генерує проблемну схему; виявлено накладання кількох
   генераторів структурованих даних на одній сторінці.

5. **Робота з AMP.** Перевірка форматів адрес через `curl -sI`, оцінка масштабу
   в індексі, і головне — **правильний порядок відключення**: спершу
   301-редирект на nginx, перевірка, і тільки потім видалення плагіна й
   `<link rel="amphtml">`. Ключ: не допустити сплеску 404.

6. **Аналіз 404 на масиві даних.** На експорті з GSC перевірено гіпотезу
   «сторінки побилися після міграції»: тренд падає, а не росте, а склад адрес
   історичний (старі `http://`-посилання, порожні дата-архіви вторинних мов,
   типоси в тексті посилань). Висновок — природний фон, а не поломка.

7. **Кореляція з інфраструктурою.** Кілька «критичних» сплесків збіглися з
   дисковим інцидентом і міграцією VPS, після стабілізації зникли самі.
   Урок: новий сплеск у GSC → спершу перевірити події на сервері.

8. **Розбір «не проіндексовано».** Чому велике число — норма: канонічні
   дублікати мультимовності, редиректи, навмисний `noindex`, закрите
   `robots.txt`. Окремо — що таке soft 404 (200 OK на порожній сторінці) і чому
   лікується `noindex`/чесним 404.

9. **Пастка перевірок.** `curl` із самого сервера йде повз CDN через локальний
   `/etc/hosts` — перевірки «як бачить світ» треба робити з зовнішньої машини.

---

## Використані команди (тільки читання)

```bash
# robots.txt і заголовки — із зовнішньої машини, через CDN
curl -s https://<domain>/robots.txt
curl -sI "https://<domain>/<path>/amp/" | grep -iE "^(HTTP|location)"
curl -sI "https://<domain>/<old-url>"   | grep -iE "^(HTTP|location)"

# інвентаризація плагінів (на сервері, від власника файлів)
sudo -u www-data wp --path=<webroot> plugin list --status=active --fields=name,version

# пошук джерела схеми в коді плагіна
grep -rl 'VideoObject' <webroot>/wp-content/plugins/<plugin>/ | head
```

## Результат

Сформульовано висновок і план: критичних проблем немає, частина закрилась сама,
решта елегантно вирішується в межах перебудови (відключення AMP → чистка схеми →
редиректи старих адрес → перенесення `robots.txt`). Окремі точкові правки зараз
сенсу не мають.

**Головний навик:** оцінювати помилки GSC за критерієм «на що це реально
впливає» і групувати виправлення за етапом робіт, а не реагувати на кожен лист.
