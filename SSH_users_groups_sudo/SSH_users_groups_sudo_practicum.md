## 1. Що таке користувачі і групи в Linux

### — як Linux розрізняє хто є хто

Linux — багатокористувацька система від народження. Кожен процес (запущена програма) і кожен файл має власника. Коли nginx віддає файл, коли cron запускає скрипт, коли ви вводите команду — ядро щоразу перевіряє: «а цьому користувачу можна?»
Важливий момент: для ядра не існує імен. Ядро оперує числами — UID та GID. Імена типу maria, backupuser, www-data — це просто зручні «етикетки» для людей, які система перекладає в числа через /etc/passwd.

### — UID, GID — що це і навіщо

UID (User ID) — унікальний номер користувача.

0 — це завжди root. Не ім'я «root» дає суперправа, а саме UID 0. Якби ви створили користувача vasya з UID 0 — він був би повноцінним root.
1–999 — системні користувачі (для служб: www-data, mysql, sshd). Вони не для людей, під ними працюють демони.
1000+ — звичайні люди. У вас maria майже напевно має UID 1000 (перший створений користувач), а backupuser, якого ви створювали в Task 4, отримав наступний вільний номер.

GID (Group ID) — те саме, але для груп. Група — це спосіб дати однакові права кільком користувачам одразу. Кожен користувач має одну основну групу (записана в passwd) і може входити в скільки завгодно додаткових (записані в group).

### — /etc/passwd і /etc/group — як читати ці файли

cat /etc/passwd
(тільки читає, безпечно)
Кожен рядок — один користувач, 7 полів через двокрапку:
maria:x:1000:1000:Maria:/home/maria:/bin/bash
backupuser:x:1001:1001:,,,:/home/backupuser:/bin/rbash
www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin
Розшифровка по полях на прикладі maria:

maria — ім'я
x — колись тут був хеш пароля, тепер він у /etc/shadow (файл читається тільки root'ом — саме тому passwd можна читати всім, а паролі — ні)
1000 — UID
1000 — GID основної групи
Maria — коментар (GECOS). Пам'ятаєте, при створенні backupuser ви писали adduser --gecos "" — це якраз «залишити коментар порожнім, не питати»
/home/maria — домашня папка
/bin/bash — shell, який запуститься при вході

Останнє поле — дуже цікаве у вашому випадку. Подивіться на три приклади вище:

maria → /bin/bash — повноцінний термінал
backupuser → /bin/rbash — restricted bash. Це ви самі зробили командою usermod -s /bin/rbash backupuser в Task 4: користувач може підключитись по SSH (щоб rsync працював), але не може міняти директорію через cd, використовувати / у шляхах команд, перевизначати PATH. Обмежена клітка.
www-data → /usr/sbin/nologin — взагалі не можна залогінитись. Це правильно для службових акаунтів: nginx-воркери працюють від www-data, але «зайти в систему як www-data» неможливо.

## 2. Права на файли

### — що означає rwxr-xr-x насправді

Що означає rwxr-xr-x насправді
Коли ви робите ls -la, перша колонка виглядає так:
-rwxr-xr-x 1 backupuser backupuser 1234 Jun 20 10:00 db_backup.sh
drwx------ 2 maria maria 4096 May 10 12:00 .ssh
Розберемо -rwxr-xr-x посимвольно:

-        rwx      r-x      r-x
  тип власник група інші

Перший символ: - файл, d директорія, l символічне посилання (ви їх бачили в /etc/nginx/sites-enabled/ — там лежать саме симлінки на конфіги).
Далі три трійки — права для трьох категорій: власник (user), група (group), всі інші (others).

Що означають літери:
ЛітераДля файлуДля директоріїr (4)читати вмістбачити список файлів усерединіw (2)змінювати вмістстворювати/видаляти файли всерединіx (1)запускати як програмузаходити в директорію (cd) і діставатись файлів
Нюанс з директоріями, який часто плутає: r без x на папці — марний (список бачиш, а відкрити файли не можеш), x без r — можна дістатись файлу, якщо знаєш точне ім'я, але список не побачиш.
Числовий запис — просто сума: r=4, w=2, x=1.

rwx = 7
r-x = 5
r-- = 4
--- = 0

Тому rwxr-xr-x = 755, rwx------ = 700, rw------- = 600.
Ви це вже застосовували в Task 1 і Task 4 з SSH-ключами:

```bash
chmod 700 /home/maria/.ssh
chmod 600 /home/maria/.ssh/authorized_keys
```

(обидві команди ЗМІНЮЮТЬ права, але це безпечна і необхідна зміна)
Чому саме так? Це не примха: sshd відмовиться приймати ключі, якщо права ширші. Логіка SSH: якщо хтось крім власника може писати в authorized_keys — значить хтось міг підкинути туди свій ключ, і файлу довіряти не можна. Тому .ssh = 700 (тільки власник), authorized_keys = 600 (читати/писати тільки власник). Приватний ключ (id_ed25519) — теж завжди 600, і в Task 2 ми це фіксували як пункт безпеки: приватний ключ сертифіката з правами 644 — це діра.

### — chmod, chown — як і навіщо

chmod (change mode) — змінює права:

```bash
chmod 750 /home/backupuser/scripts/db_backup.sh
```

(ЗМІНЮЄ права на файл; на роботу сайту не впливає)
Можна і літерами: chmod u+x script.sh — додати власнику право виконання. Ви так робили chmod +x для всіх бекап-скриптів у Task 4 — без x bash-скрипт не можна запустити напряму (хоча bash script.sh спрацює і без x, бо тоді запускається bash, який просто читає файл).
chown (change owner) — змінює власника і/або групу:

```bash
chown -R backupuser:backupuser /home/backupuser/
```

(ЗМІНЮЄ власника рекурсивно (-R) для всього дерева папок)
Цю команду ви виконували в Task 4 кілька разів — і це було критично: скрипти й папки ви створювали від root, а працювати з ними мав backupuser. Без chown backupuser не зміг би писати у власні логи.
Формат: chown власник:група шлях. Можна тільки власника (chown maria file) або тільки групу (chown :www-data file).

### — чому 750 безпечніше ніж 755

Різниця рівно в одній цифрі — правах для «всіх інших»:

755 = rwxr-xr-x — власник усе, група читає+заходить, і будь-який користувач системи теж читає+заходить
750 = rwxr-x--- — власник усе, група читає+заходить, всі інші — нічого

Чому це важливо на реальному сервері: у вас в системі живуть www-data (від нього працюють nginx-воркери і PHP), mysql, backupuser та інші. Якщо WordPress зламають через дірявий плагін — зловмисник отримує можливість виконувати команди від імені www-data. І тепер питання: що www-data зможе прочитати?

Якщо /home/backupuser/backups/ має 755 — зламаний WordPress прочитає ваші дампи бази (а там усі хеші паролів користувачів сайту).
Якщо 750 (і www-data не в групі backupuser) — не прочитає нічого.

Це називається принцип найменших привілеїв: кожен користувач/процес має рівно стільки прав, скільки треба для роботи, і ні краплі більше. Ваша схема з backupuser у Task 4 — саме реалізація цього принципу: окремий користувач, rbash замість повного shell, свій ключ тільки для rsync.
Згадайте також вашу logrotate-конфігурацію з Task 4: create 0640 root root — нові лог-файли створюються з правами 640 (rw-r-----), тобто «інші» навіть прочитати лог не можуть. Та сама ідея.
Подивитись, де зараз «дірки», можна так:

```bash
ls -la /home/backupuser/ /home/backupuser/backups/
```

(тільки читає) — перевірте треті трійки прав. Якщо десь r-x для others на папках з бекапами — варто затягнути до 750.

## 3. sudo — що це і як працює

### — різниця між root і sudo

root — це користувач з UID 0, для якого ядро не перевіряє права взагалі. Будь-який файл, будь-який процес, будь-який порт.
sudo (superuser do) — це програма, яка дозволяє звичайному користувачу виконати окрему команду від імені іншого користувача (за замовчуванням — root), попередньо перевіривши, чи є в нього таке право.
Чому «працювати під root постійно» — погана практика, а «maria + sudo» — хороша:

Аудит. Кожен виклик sudo пишеться в лог (/var/log/auth.log). Видно: хто, коли, яку команду. Коли всі сидять під root — у логах просто «root зробив», і не зрозуміло хто саме.
Захист від помилки. rm -rf з одруком під root знищує систему. Під звичайним користувачем — впирається в права. Ваш інцидент з Task 4.1 (rm -rf /home/oleh/ поклав файлову систему) — приклад того, наскільки руйнівними бувають операції під root; sudo хоча б змушує на секунду задуматись перед кожною такою командою.
Менше вікно атаки. Якщо викрадуть ключ maria — зловмиснику ще треба її пароль для sudo. Якщо викрадуть ключ root — усе одразу.

Саме тому стандартна рекомендація, яку ви частково реалізували: SSH-вхід для root вимкнений (PermitRootLogin no в sshd_config), заходить maria, підвищується через sudo.
До речі, ви вже активно користувались одним корисним патерном:

```bash
sudo -u backupuser bash /home/backupuser/scripts/sync_backup.sh
```

(запускає скрипт; чи змінює щось — залежить від скрипта) — прапорець -u означає «виконати не від root, а від вказаного користувача». Ви так тестували всі скрипти backupuser'а в Task 4 — і це правильний спосіб: перевірити, що скрипт працює саме з правами backupuser, а не з всемогутністю root. Якби ви тестували від root, а cron потім запускав від backupuser — могли б зловити «у тесті працювало, вночі впало з Permission denied».

### — /etc/sudoers — як обмежити права

Це конфіг, який визначає: хто, на якому хості, від чийого імені, які команди може виконувати.

_Важливо: ніколи не редагуйте його через nano /etc/sudoers. Тільки:_

```bash
sudo visudo
```

(відкриває sudoers на редагування, ЗМІНЮЄ систему) — visudo перед збереженням перевіряє синтаксис. Помилка в sudoers = ніхто не може отримати root = ви заблокували самі себе на сервері. visudo від цього захищає.

Читання сучасного стану:

```bash
sudo cat /etc/sudoers
sudo ls -la /etc/sudoers.d/
```

(тільки читає)
Типові рядки і їх розшифровка:
root ALL=(ALL:ALL) ALL
%sudo ALL=(ALL:ALL) ALL
Формат: хто де=(від*кого:від*якої_групи) що

%sudo — знак % означає групу. Тобто «всі члени групи sudo можуть на будь-якому хості від імені будь-кого виконувати будь-що». Ось чому членство maria в групі sudo (з /etc/group) = повні права.

А тепер найцікавіше — обмежене sudo. Приклад, який прямо стосується вашої схеми бекапів. Уявімо, ви хочете, щоб backupuser міг перезапустити nginx після оновлення сертифіката, але більше нічого:
backupuser ALL=(root) NOPASSWD: /usr/sbin/nginx -s reload
Це означає: backupuser може виконати sudo nginx -s reload без пароля — і тільки цю команду. Спроба sudo rm -rf / буде відхилена. Так будують автоматизацію безпечно: скрипту-роботу дають одну конкретну команду замість повного root.
Перевірити, що дозволено поточному користувачу:

```bash
sudo -l
```

(тільки читає) — виводить список ваших sudo-привілеїв.

## 4. SSH — як працює аутентифікація

### — пара ключів: публічний і приватний

SSH з ключами — це асиметрична криптографія, той самий принцип, що і в TLS-сертифікатах з Task 2 (там теж публічний ключ у сертифікаті + приватний на сервері).

Приватний ключ (id_ed25519, myproject) — секрет. Лежить у того, хто підключається. Нікому ніколи не передається. Права 600.
Публічний ключ (id_ed25519.pub, myproject.pub) — не секрет. Його можна показувати кому завгодно, публікувати, пересилати. Лежить на сервері, до якого підключаються.

Математичний фокус: те, що зашифровано/підписано приватним ключем, перевіряється публічним — але з публічного ключа приватний вивести неможливо (за розумний час).
Як відбувається вхід (спрощено):

Клієнт каже: «хочу зайти як backupuser, ось мій публічний ключ»
Сервер дивиться в authorized_keys цього користувача: чи є там такий ключ?
Якщо є — сервер генерує випадкове число (challenge) і шле клієнту: «підпиши це своїм приватним ключем»

Клієнт підписує, сервер перевіряє підпис публічним ключем
Підпис зійшовся → значить, у клієнта справді є приватна половина → пускаємо

Пароль ніколи не передається (бо його немає). Приватний ключ теж ніколи не передається по мережі — тільки підпис. Тому перехопити трафік — марно.
Ви цю схему повністю збудували руками в Task 4:

```bash
sudo -u backupuser ssh-keygen -t ed25519 -C "backupuser@myproject-old" -f /home/backupuser/.ssh/id_ed25519 -N ""
```

(СТВОРЮЄ два файли ключів, більше нічого в системі не змінює)
Розшифровка: -t ed25519 — тип ключа (сучасний, короткий і швидкий алгоритм; старіший аналог — RSA); -C — просто текстовий коментар, щоб потім в authorized_keys було видно чий це ключ; -f — куди покласти; -N "" — порожня passphrase, тобто приватний ключ не зашифрований паролем. Для автоматики (cron + rsync) інакше не можна — нікому вводити пароль о 4 ранку. Компенсація ризику — саме той обмежений rbash і принцип найменших привілеїв з розділів 1–2.

### — authorized_keys — що це

Простий текстовий файл: ~/.ssh/authorized_keys у домашній папці користувача на сервері. Кожен рядок — один публічний ключ, якому дозволено заходити під цим користувачем:
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA...XXXXX backupuser@myproject-old
Три частини: тип ключа, сам ключ (base64), коментар.
Логіка проста: скільки рядків — стільки «дверей». Можна додати ключі кількох людей/машин до одного акаунта. Видалив рядок — відкликав доступ (це, до речі, головна перевага над паролями: щоб забрати доступ у людини, не треба міняти пароль усім — просто видаляєш її рядок).

Ви працювали з цим файлом двічі:

Task 1 — у rescue mode через chroot додавали свій ключ до maria на клонованій системі (echo "КЛЮЧ" >> authorized_keys), бо інакше після перезавантаження не було б як зайти.
Task 4 — додавали публічний ключ старого сервера до backupuser на новому, щоб rsync ходив без пароля.

Зверніть увагу на >> (додати в кінець) а не > (перезаписати) — з > ви б стерли всі наявні ключі, включно з тим, яким самі заходите. Класична помилка, яка відрізає доступ до сервера.

### — sshd_config — які параметри що означають

Файл /etc/sshd/sshd_config... точніше /etc/ssh/sshd_config — конфіг серверної частини SSH (демона sshd). Не плутати з /etc/ssh/ssh_config — то налаштування клієнта.

```bash
sudo grep -vE '^#|^$' /etc/ssh/sshd_config
```

(тільки читає) — показує конфіг без коментарів і порожніх рядків, зручно для огляду.
Ключові параметри — і всі вони вам знайомі з Task 1, де ви перевіряли їх на снапшоті перед першим запуском:
Port 2222 — на якому порту слухає sshd. Стандарт — 22. Ваш нестандартний порт не є «справжньою безпекою» (nmap знайде за хвилину), але відсікає 99% автоматичних ботів, які довбляться саме в 22. У Task 4.1 зверніть увагу: rescue mode хостера — це інша система з дефолтним конфігом, тому там ви заходили на порт 22, а не 2222. Гарна ілюстрація що порт — властивість конфігурації системи, а не машини.
PermitRootLogin no — чи можна заходити напряму root'ом. no — правильне значення (тоді єдиний шлях до root: зайти як maria → sudo). Бонусні варіанти: prohibit-password — root може, але тільки по ключу.
AllowUsers maria backupuser — білий список: хто взагалі може підключатись. Усіх інших sshd відхилить ще до перевірки ключів. Ви це перевіряли командою grep -i allowusers /mnt/etc/ssh/sshd_config у Task 1. Важлива практична деталь: коли ви створювали backupuser, якщо на сервері є AllowUsers — його треба було туди дописати, інакше ключі правильні, а вхід не працює.
PubkeyAuthentication yes — дозволити вхід по ключах. Це те, що ви перевіряли через grep -i pubkey.
PasswordAuthentication no — заборонити вхід по паролях взагалі. Найважливіший параметр захисту: боти перебирають паролі цілодобово, а от приватний ключ ed25519 перебрати неможливо. Якщо у вас тут yes — варто обговорити вимкнення (але обережно: спочатку переконатись, що ключі працюють, інакше можна замкнути себе зовні).
Після будь-якої зміни sshd_config:

```bash
sudo sshd -t
```

(тільки читає/перевіряє) — валідація синтаксису конфіга, аналог nginx -t.

```bash
sudo systemctl reload sshd
```

(ЗМІНЮЄ: перечитує конфіг сервера SSH; поточні сесії не рве, але помилковий конфіг може заблокувати нові підключення)
Золоте правило, яке напряму випливає з вашого досвіду Task 1: змінюючи sshd_config — не закривайте поточну SSH-сесію, поки в другому терміналі не переконались, що нове підключення працює. Поточна сесія — ваша страховка.

## Backup - існує системний користувач такий, з'ясуваті ролі, якщо не потрібні видалили (новий сервер проєкту)

або перенести логіку бекапів в цього користувача.

Аналіз користувача backup
backup:x:34:34:backup:/var/backups:/usr/sbin/nologin
Це системний користувач Linux — він існує за замовчуванням в кожному Debian. Ось що про нього відомо:
ПараметрЗначенняЩо означаєUID34Системний користувач (не людина)Домашня папка/var/backupsСаме там системні бекапи apt, dpkgShell/usr/sbin/nologinНе може логінитись — ні через термінал, ні через SSHCron задачінемаєНічого не робить заразФайлинемаєНічим не керує
/var/backups/ — це його домашня папка, але всі файли там належать root, не backup.

Висновок — чи можна використати?
Ні, цей користувач не підходить для нашої схеми з двох причин:

1. /usr/sbin/nologin — він не може підключатись по SSH. А нам потрібно щоб старий сервер заходив по SSH на новий і забирав бекапи.
2. Це системний користувач якого використовує сама система Debian для своїх потреб. Чіпати його — погана практика.
