# HSTS і Cloudflare SSL/TLS — конспект-практикум

Розбір налаштувань SSL/TLS на сайтах за Cloudflare: що означає статистика
«Traffic Served Over TLS», як працює HSTS, HSTS Preload і як діагностувати
зайві/відсутні заголовки безпеки.

---

## 1. Cloudflare SSL/TLS → Overview: Traffic Served Over TLS

У розділі **SSL/TLS → Overview** Cloudflare показує статистику запитів за
версіями TLS. Категорії:

- **TLS 1.3** — найсучасніший, найбезпечніший
- **TLS 1.2** — поточний стандарт
- **TLS 1.1 / 1.0** — застарілі
- **None (not secure)** — з'єднання без шифрування (звичайний HTTP на порту 80)

### Що означає «None (not secure) — N запитів»

Це запити, що прийшли на `http://example.com/...` замість
`https://example.com/...`. Ділянка шляху «відвідувач → Cloudflare» пройшла без
шифрування; далі Cloudflare зазвичай робить редирект 301 на HTTPS, і користувач
потрапляє на захищене з'єднання.

### Це нормально?

**Так, такий трафік практично неминучий:**

1. **Боти та сканери** — пошукові краулери (роботи), сканери безпеки, спам-боти часто
   стукають спочатку на HTTP.
2. **Старі посилання** — десь в інтернеті залишилися посилання `http://...`.
3. **Прямий ввід адреси** — користувач друкує домен без протоколу, браузер
   за замовчуванням пробує HTTP.
4. **Атаки і спроби експлойтів** — багато автоматичного шуму на порт 80.

Головне — щоб цей HTTP-трафік **коректно редиректився на HTTPS**, а не
віддавався у відкритому вигляді.

## 2. Базова перевірка: чи працює редирект HTTP → HTTPS

```bash
curl -I http://example.com/
```

**Розшифровка:**
- `curl` — утиліта для HTTP-запитів
- `-I` — запитати тільки заголовки відповіді (HEAD-запит), без тіла сторінки
- Команда **тільки читає**, нічого не змінює, на роботу сайту не впливає

### Гарна відповідь

```
HTTP/1.1 301 Moved Permanently
Location: https://example.com/
```

`301` + `Location: https://...` — редирект на HTTPS працює.

### Погана відповідь

```
HTTP/1.1 200 OK
```

200 без редиректу — сайт віддає контент незахищеним каналом. Потрібно вмикати
**Always Use HTTPS** в Cloudflare (або налаштовувати редирект на рівні
веб-сервера).

---

## 3. Cloudflare: ключові опції для HTTPS

**Cloudflare → SSL/TLS → Edge Certificates:**

- **Always Use HTTPS** — примусовий 301-редирект усього HTTP на HTTPS. Базове
  й обов'язкове налаштування.
- **Automatic HTTPS Rewrites** — автоматично переписує `http://` посилання
  всередині HTML-сторінок на `https://`. Захищає від mixed content.
- **HTTP Strict Transport Security (HSTS)** — вмикається обережно (див. нижче).

**SSL/TLS → Overview — режими:**

- **Off** — без шифрування. Не використовувати.
- **Flexible** — CF ↔ сервер по HTTP. **Небезпечно**, залишає дірку між CF
  і сервером.
- **Full** — CF ↔ сервер по HTTPS, але сертифікат на сервері **не перевіряється**.
  Захищає від перехоплення, але не від MITM на ділянці CF↔origin.
- **Full (Strict)** — CF ↔ сервер по HTTPS з **перевіркою сертифіката**.
  Рекомендований варіант для продакшну.

## 4. HSTS — HTTP Strict Transport Security

### Що це

Заголовок відповіді, який каже браузеру: «працюй із цим сайтом лише по
HTTPS протягом N секунд».

Приклад заголовка:
```
Strict-Transport-Security: max-age=31536000; includeSubdomains;
```

- `max-age=31536000` — 365 днів (у секундах)
- `includeSubdomains` — правило поширюється на всі піддомени
- `preload` (опціонально) — заявка на включення до preload-списку браузерів

### Як це працює

1. Користувач один раз заходить на `https://example.com`.
2. Сервер у відповіді надсилає HSTS-заголовок.
3. Браузер запам'ятовує: «цей сайт сказав — N секунд працювати лише по HTTPS».
4. Після цього:
   - Якщо ввести `http://example.com` — браузер **сам, ще до відправлення запиту**,
     переробить його на `https://`.
   - При помилці сертифіката браузер **не дасть** її обійти (немає кнопки «все
     одно перейти»).

### Що буде, якщо HSTS не ввімкнено

Сайт залишається вразливим до **атаки SSL Stripping**:

1. Користувач друкує `example.com` (без протоколу).
2. Браузер за замовчуванням пробує HTTP.
3. Зловмисник у тій самій Wi-Fi мережі (кав'ярня, аеропорт, скомпрометований
   роутер) **перехоплює цей перший HTTP-запит**, сам спілкується із сайтом по
   HTTPS, а користувачеві показує HTTP-версію.
4. Трафік користувача йде через атакувальника у відкритому вигляді; користувач
   бачить звичний сайт і нічого не помічає.

### Обмеження HSTS

HSTS захищає лише якщо користувач **уже хоча б раз** успішно зайшов на сайт
по HTTPS і отримав заголовок. **Перший візит залишається вразливим.** Це вирішує
HSTS Preload (див. нижче).

---

## 5. HSTS Preload

### Що це

Список доменів, **зашитий прямо в код браузерів** (Chrome, Firefox, Safari,
Edge). Для доменів зі списку HTTPS обов'язковий із **найпершого візиту** —
браузер взагалі ніколи не надішле HTTP-запит до цього домену.

### Перевірка домену

Відкрити в браузері:

```
https://hstspreload.org/?domain=example.com
```

Можливі статуси:
- `currently preloaded` — домен у списку.
- `eligible for preloading` — підходить, але ще не подано.
- `not preloaded` — не в списку.

### Вимоги для потрапляння в Preload

1. Валідний сертифікат на основному домені і всіх піддоменах.
2. Редирект з HTTP на HTTPS на тому самому хості.
3. HSTS-заголовок на HTTPS-відповіді з усіма трьома директивами:
   - `max-age` ≥ `31536000` (1 рік, але рекомендується 2)
   - `includeSubDomains`
   - `preload`

### Важливо про вихід з Preload

Видалити домен із preload-списку — процедура на **тижні/місяці** через подання
заявки в Chromium. Подавати домен у Preload варто, лише коли ви абсолютно
впевнені, що **всі** піддомени працюють по HTTPS і працюватимуть надалі.

## 6. Кейс: попередження «Unnecessary HSTS header over HTTP»

### Текст попередження

```
Warning: Unnecessary HSTS header over HTTP
The HTTP page at http://example.com sends an HSTS header.
This has no effect over HTTP, and should be removed.
```

### Що сталося

При запиті `curl -I http://example.com/` у відповіді прийшов рядок:

```
Strict-Transport-Security: max-age=31536000; includeSubdomains;
```

Заголовок HSTS надіслано на **HTTP-відповідь**, а не лише на HTTPS.

### Чому це вважається помилкою

За специфікацією **RFC 6797** браузери мають **ігнорувати** HSTS-заголовок,
отриманий незашифрованим HTTP. Логіка: якщо з'єднання не захищене, то
й заголовку, що прийшов ним, довіряти не можна — атакувальник міг його
підробити або підмінити параметри.

HSTS має сенс **лише у відповіді по HTTPS**. На HTTP він:
- Браузером ігнорується (марний).
- Може ввести в оману адміністраторів («здається, що працює»).
- Вважається дрібним порушенням best practices.

### Це критично?

**Ні, не критично.** Це `Warning`, а не `Error`. Сайт залишається в Preload,
захист HSTS працює на повну силу через HTTPS-відповіді. Це «косметична»
претензія — зайвий заголовок на 301-редиректі.

## 7. Діагностика: звідки йде зайвий HSTS-заголовок

Заголовок може встановлюватися у двох місцях:

1. **На сервері** (nginx/apache — директивою `add_header` та аналогами).
2. **У Cloudflare** (через налаштування HSTS у SSL/TLS → Edge Certificates).

### Крок 1. Пошук у конфігу nginx

```bash
sudo grep -r -i "strict-transport-security\|add_header.*Strict" /etc/nginx/
```

**Розшифровка:**
- `sudo` — потрібні права root для читання конфігів nginx
- `grep -r` — рекурсивний пошук у всіх файлах папки
- `-i` — ігнорувати регістр
- `"strict-transport-security\|add_header.*Strict"` — шукаємо або сам заголовок,
  або директиву `add_header`, яка його встановлює
- `/etc/nginx/` — папка з конфігами nginx
- **Тільки читає конфіги, на сайт не впливає**

**Результати:**
- Якщо nginx сам встановлює HSTS — побачите рядки
  `add_header Strict-Transport-Security ...` у якомусь `.conf` файлі.
- Якщо нічого не знайдено — заголовок встановлює Cloudflare.

### Крок 2. Порівняти HTTP та HTTPS відповіді

```bash
echo "=== HTTP ==="
curl -sI http://example.com/ | grep -i "server\|strict"
echo ""
echo "=== HTTPS ==="
curl -sI https://example.com/ | grep -i "server\|strict"
```

**Розшифровка:**
- Два HEAD-запити — на HTTP і на HTTPS.
- `-s` — тихий режим (без прогрес-бара).
- `-I` — тільки заголовки.
- `grep -i "server\|strict"` — фільтруємо тільки рядки `Server:` і HSTS.
- **Тільки читає**, на сайт не впливає.

На що дивитися:
- Чи різний `Server:` у двох відповідей (одна може йти через CF, інша — ні,
  це пояснить розбіжність у джерелі заголовків).
- На яких відповідях узагалі є HSTS — лише на HTTPS (правильно) чи ще й на
  HTTP (те саме попередження).

### Крок 3. Перевірити подробиці HSTS

```bash
curl -sI https://example.com/ | grep -i strict
```

**Розшифровка:**
- HEAD-запит на HTTPS, фільтр за рядком із HSTS.
- **Тільки читає**, на сайт не впливає.

На що дивитися: чи є у значенні директива `preload` — потрібна для потрапляння
до Preload-списку.

## 8. Як виправити (зміни, впливають на сайт!)

> ⚠️ Усі правки конфігів **змінюють поведінку сайту**. Перед змінами робити
> бекап конфігів і перевіряти `nginx -t` (перевірка конфігураційних файлів Nginx на наявність синтаксичних помилок перед тим, як застосувати зміни на живому сервері) до перезавантаження.

### Випадок 1. HSTS встановлює nginx

У конфігах буде блок виду:

```nginx
server {
    listen 80;
    server_name example.com;

    # ❌ HSTS тут не потрібен — це HTTP-сервер
    add_header Strict-Transport-Security "max-age=31536000; includeSubdomains" always;

    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name example.com;

    # ✅ HSTS тут — правильно
    add_header Strict-Transport-Security "max-age=31536000; includeSubdomains" always;
    ...
}
```

**Що зробити:** прибрати `add_header Strict-Transport-Security ...` з блоку
`listen 80;`. У HTTP-блоці має бути **лише редирект** на HTTPS, без заголовків
безпеки.

**Перевірка конфігу перед перезавантаженням (тільки читає):**
```bash
sudo nginx -t
```

**Перезавантаження (змінює — але без даунтайму для наявних з'єднань):**
```bash
sudo systemctl reload nginx
```

### Випадок 2. HSTS встановлює Cloudflare

Зазвичай Cloudflare сам дотримується специфікації і не встановлює HSTS на
HTTP-відповіді. Якщо встановлює — це рідкісна ситуація; перевірити налаштування
у SSL/TLS → Edge Certificates → HSTS і за потреби вимкнути/налаштувати заново.

---

## 9. Чек-лист коректного налаштування HTTPS

- [ ] `curl -I http://example.com/` повертає `301` і `Location: https://...`
- [ ] Cloudflare SSL/TLS режим — `Full (Strict)`, не `Flexible` і не просто `Full`
- [ ] Увімкнено `Always Use HTTPS`
- [ ] Увімкнено `Automatic HTTPS Rewrites` (якщо є mixed content)
- [ ] HSTS присутній **лише на HTTPS-відповідях**
- [ ] HSTS містить `max-age` ≥ 31536000, `includeSubDomains`, за бажання `preload`
- [ ] Усі піддомени реально працюють по HTTPS (особливо важливо для
      `includeSubDomains`)
- [ ] Якщо домен у Preload — це усвідомлене рішення, оборотне лише через довгу
      процедуру

---

## 10. Шпаргалка команд (усі тільки читають, на сайт не впливають)

```bash
# Перевірка редиректу HTTP → HTTPS
curl -I http://example.com/

# Перевірка HTTPS-відповіді цілком
curl -I https://example.com/

# Тільки HSTS-заголовок на HTTPS
curl -sI https://example.com/ | grep -i strict

# Порівняння HTTP і HTTPS відповідей
curl -sI http://example.com/  | grep -i "server\|strict"
curl -sI https://example.com/ | grep -i "server\|strict"

# Пошук HSTS у конфігах nginx (потребує sudo)
sudo grep -r -i "strict-transport-security\|add_header.*Strict" /etc/nginx/

# Перевірка валідності конфігу nginx (потребує sudo)
sudo nginx -t

# Перевірка домену в HSTS Preload (через браузер)
# https://hstspreload.org/?domain=example.com
```
