# Щоденний чек-лист перевірки нового сервера (203.0.113.20)

Виконувати кожного ранку протягом тижня після інциденту з файловою системою
(30 червня 2026). Усі команди — тільки читання, нічого не змінюють.

---

## 1. Чи сервер не перезавантажувався вночі

```bash
uptime
```
**На що дивитись:** значення "up" має бути більше доби (наприклад `up 1 day`).
Якщо там щось типу `up 5 min` або `up 23 min` — сервер перезавантажувався
вночі без твоєї участі, це сигнал що щось трапилось.

```bash
last reboot | head -5
```
**На що дивитись:** час останнього `system boot`. Якщо він припадає на ніч
або на час роботи cron-завдань (01:30, 02:22, 03:20) — це збіг, який треба
розслідувати далі.

---

## 2. Чи були нові помилки файлової системи

```bash
dmesg | grep -iE "ext4-fs error|bad block|remount-ro" | tail -20
```
**На що дивитись:** якщо команда повертає порожній результат — все добре.
Якщо є рядки типу `EXT4-fs error` або `remount-ro` — файлова система знову
зловила помилку, навіть якщо сайт зараз працює.

---

## 3. Чи відпрацювали нічні бекапи без помилок

```bash
tail -20 /home/backupuser/backups/logs/uploads_backup.log
```
**На що дивитись:** має бути `Backup completed successfully` і фінальний
розмір (~112G, плюс трохи більше з часом). Жодного `ERROR`.

```bash
tail -20 /home/backupuser/backups/logs/db_backup.log
```
**На що дивитись:** `Dump created`, `Compressed`, без `ERROR`.

```bash
tail -20 /home/backupuser/backups/logs/systembackup.log
```
**На що дивитись:** `Archive created`, без `ERROR`.

---

## 4. Стан диска і пам'яті

```bash
df -h
```
**На що дивитись:** використання `/dev/sda1` не повинно стрімко зростати
день у день без причини (нормальний повільний ріст через нові фото — це ок,
різкий скачок на 10-20% за добу — питання).

```bash
free -h
```
**На що дивитись:** `available` пам'яті не повинно бути критично малим.

---

## 5. Сайт і сервіси

```bash
curl -sI https://example.com/ | head -5
```
**На що дивитись:** має бути `HTTP/1.1 301` (редирект на https) або `200`,
без таймаутів і без `522`.

```bash
systemctl status nginx mysql --no-pager | grep -E "Active|Loaded"
```
**На що дивитись:** обидва мають бути `active (running)`.

---

## Якщо щось пішло не так

- Якщо знову `EXT4-fs error` або сервер сам перезавантажився — зафіксувати
  точний час і вміст помилки з `dmesg`, це знадобиться для звернення до хостинг-провайдера.
- Якщо бекап вночі впав з `ERROR` — перевірити вільне місце на диску
  (`df -h`) і чи сервер не перезавантажувався саме в момент бекапу.
- Якщо сайт недоступний (`522` або таймаут) — спочатку перевірити
  `systemctl status nginx mysql`, потім `dmesg` на помилки диска.

## Після тижня спостереження

Якщо жодних нових `EXT4-fs error` і перезавантажень не було — можна вважати
що розбиття бекапу по роках (з паузами) достатньо знизило навантаження, і
переходити до наступного кроку (синхронізація на старий сервер). Якщо
помилки повторювались хоч раз — варто звернутись в підтримку хостинг-провайдера з логами
до того, як рухатись далі.
