# Практикум: повторювані падіння VPS через пошкодження файлової системи EXT4 — діагностика та вирішення

> Узагальнений конспект реального інциденту. Усі імена серверів, IP-адреси,
> домени, шляхи та номери тикетів замінені на умовні.

## Передісторія

Новий сервер (`vps-new`, IP `203.0.113.10`) створений через снапшот зі старого
сервера (`vps-old`, IP `198.51.100.20`) у хостинг-провайдера. З моменту
створення сервер періодично падав з EXT4 помилками файлової системи.

## Резюме першого інциденту і рішення (деградація файлової системи при видаленні файлів)

### Що сталося

При видаленні великої папки `/home/username/` (16GB) команда `rm -rf`
наткнулась на **приховані пошкодження файлової системи EXT4** на диску `sdb1`,
які вже існували до цього — швидше за все з'явились ще при міграції через
снапшот провайдера.

Ядро Linux виявило помилку CRC (контрольна сума не збіглась) і **автоматично
перемонтувало весь розділ у режим read-only** — це вбудований захисний механізм
щоб не пошкодити дані ще більше.

### Що це спричинило

- MariaDB не змогла запуститись — `/tmp` і журнал були недоступні для запису
- SSH перестав відповідати
- Сайт впав з помилкою `Error establishing a database connection`
- Звичайний reboot через панель провайдера не допоміг — диск залишався read-only

### Як вирішили

1. Зайшли в панель провайдера → переключили boot у **Rescue mode**
2. Підключились по SSH на стандартний порт 22 з тимчасовим паролем
3. Запустили перевірку та відновлення файлової системи:
   ```bash
   fsck -y /dev/sdb1
   ```
   `fsck` виправив усі помилки — orphaned inodes, bitmap differences, CRC
4. Повернули boot у **LOCAL** через панель провайдера
5. Після звичайного завантаження MariaDB піднялась сама, сайт запрацював

### Головний висновок

`rm -rf` **не була причиною** пошкодження — вона лише стала тригером який
виявив приховану проблему диска. Сайт міг впасти в будь-який інший момент при
будь-якій активній операції з файлами.

## Етап 2 — виявлення чергового падіння

### Що виявили

Під час щоденної перевірки виявлено що сервер перезавантажився вночі:

```
reboot   system boot  4.19.0-17-cloud- Thu <день N> 02:55   still running
```

`uptime` показав лише `up 8:26` замість очікуваних кількох діб.

### Аналіз логів через persistent journal

Напередодні ми налаштували persistent systemd journal, тому вперше змогли
побачити логи попереднього завантаження:

```bash
sudo journalctl -b -1 --no-pager | grep -iE "error|fail|killed|oom|crash|ext4" | tail -30
```

Результат показав що журнал **обривається о 02:50:44** — за 4 хвилини до
перезавантаження о 02:55 — без жодних записів про помилки. Це класична ознака
що файлова система пішла в read-only і journald більше не міг писати на диск.

З попереднього завантаження знайшли:

```
kernel: EXT4-fs (sda1): INFO: recovery required on readonly filesystem
kernel: EXT4-fs (sda1): orphan cleanup on readonly fs
kernel: EXT4-fs (sda1): 5 orphan inodes deleted
kernel: EXT4-fs (sda1): recovery complete
```

### Повна хронологія перезавантажень

Перевірка `last reboot` показала повну картину з моменту міграції
(дати умовні, відносно дня міграції — День 0):

| День 0   | 17:29, 18:21        | Нормально — перезавантаження при міграції          |

| День 64  | 11:10, 11:37, 11:50 | 3 падіння за 40 хвилин — без активності            |

3-4 дні, навіть без будь-якої активності.

## Переписка з провайдером

### Перше звернення (тикет №1)

Ми надіслали детальний тикет з:

- Повною хронологією перезавантажень
- Логами EXT4 помилок з dmesg і journal
- Поясненням що деякі падіння спричинені нашими діями, але більшість — без жодної активності
- Прямим зв'язком з попереднім інфраструктурним інцидентом провайдера

### Перша відповідь провайдера (відхилена)

Провайдер відповів що розгорнув плановий патч безпеки вночі, що могло
спричинити короткий перебій. Запропонував це як вирішення проблеми.

**Ми відхилили** цю відповідь, пояснивши що патч пояснює лише одне
перезавантаження (останнє), але не вирішує основну проблему — EXT4 помилки
які тривають вже понад місяць.

### Друга відповідь провайдера (прийнята)

> _"Based on the description of the issue you provided, we have migrated your VPS
> to another host. However, we recommend running an fsck to check the integrity
> of the files."_

Провайдер підтвердив проблему і **мігрував VPS на інший фізичний хост**.

## Фінальний етап — вирішення проблеми

### Порядок дій

**Крок 1 — Синхронізація медіафайлів**

Перед переключенням DNS синхронізували медіафайли зі старого сервера:

```bash
sudo bash /home/backupuser/scripts/sync_uploads.sh
```

Результат: `Sync completed successfully` — сервери синхронізовані.

**Крок 2 — Переключення DNS на старий сервер**

У DNS-панелях змінили A-записи на IP старого сервера `198.51.100.20`:

- `example.com` → `198.51.100.20`
- `www.example.com` → `198.51.100.20`
- `example.org` → `198.51.100.20`
- `www.example.org` → `198.51.100.20`

**Крок 3 — Оновлення SSL сертифіката на старому сервері**

Після поширення DNS запустили оновлення сертифіката:

```bash
sudo certbot renew --force-renewal
```

Результат: `Congratulations, all renewals succeeded` ✅

**Крок 4 — fsck на новому сервері в Rescue mode**

Переключили новий сервер в Rescue mode через панель провайдера.
Підключились по SSH і запустили перевірку:

```bash
fsck -y /dev/sdb1
```

Результат:

```
/dev/sdb1: clean, 2061473/22937600 files, 64724611/91750139 blocks
```

**`clean`** — файлова система чиста після міграції на новий хост ✅

**Крок 5 — Повернення в нормальний режим**

Перезавантажили новий сервер з rescue mode в normal mode через панель провайдера.

**Крок 6 — Переключення DNS назад на новий сервер**

Повернули всі A-записи на `203.0.113.10`.

**Крок 7 — Перевірка**

```bash
sudo tail -5 /www/example.com/logs/access.log
```

Підтверджено живий трафік на новому сервері — реальні відвідувачі
отримують сторінки з кодом `200` ✅

## Висновок

Проблема була апаратною — пошкоджене фізичне сховище під VPS, найімовірніше
внаслідок інфраструктурного інциденту хостинг-провайдера.

Після міграції на новий фізичний хост і перевірки fsck:

- Файлова система чиста (`clean`)
- Сервер працює стабільно
- Сайт отримує живий трафік

**Рекомендація:** продовжувати щоденний моніторинг за чек-листом протягом
наступного тижня щоб переконатись що падіння не повторюються.

## Ключові уроки практикуму

1. **Read-only remount — захисний механізм ядра**, а не сама помилка: шукайте
   першопричину в стані диска/сховища.
2. **Persistent systemd journal** налаштовуйте одразу — без нього логи
   попереднього завантаження втрачаються, і діагностика "нічних" падінь
   неможлива.
3. **Обрив журналу без записів про помилки** за кілька хвилин до падіння —
   класична ознака переходу ФС у read-only.
4. **Хронологія `last reboot` + контекст активності** — сильний аргумент у
   переписці з провайдером: вона відрізняє падіння "від наших дій" від падінь
   "без активності".
5. **Не приймайте першу зручну відповідь провайдера**, якщо вона пояснює лише
   один епізод, а не паттерн.
6. **Перед роботами на проді** — синхронізація даних і тимчасове переключення
   DNS на резервний сервер мінімізують простій.
7. **fsck запускайте лише з Rescue mode** (на відмонтованому розділі), ніколи
   на живій змонтованій ФС.
