# Резюме інциденту і рішення в моєму випадку — 26 червня 2026 (деградація файлової системи при видаленні файлів)

## Що сталося

При видаленні великої папки `/home/olduser/` (16GB) команда `rm -rf` наткнулась на **приховані пошкодження файлової системи EXT4** на диску `sdb1`, які вже існували до цього — швидше за все з'явились ще при міграції через снапшот хостинг-провайдера 30 березня 2026.

Ядро Linux виявило помилку CRC (контрольна сума не збіглась) і **автоматично перемонтувало весь розділ у режим read-only** — це вбудований захисний механізм щоб не пошкодити дані ще більше.

## Що це спричинило

- MariaDB не змогла запуститись — `/tmp` і журнал були недоступні для запису
- SSH перестав відповідати
- Сайт впав з помилкою `Error establishing a database connection`
- Звичайний reboot через панель хостинг-провайдера не допоміг — диск залишався read-only

## Як вирішили

1. Зайшли в панель хостинг-провайдера → переключили boot у **Rescue mode**
2. Підключились по SSH на стандартний порт 22 з тимчасовим паролем
3. Запустили перевірку та відновлення файлової системи:
   ```bash
   fsck -y /dev/sdb1
   ```
   `fsck` виправив усі помилки — orphaned inodes, bitmap differences, CRC
4. Повернули boot у **LOCAL** через панель хостинг-провайдера
5. Після звичайного завантаження MariaDB піднялась сама, сайт запрацював

## Головний висновок

`rm -rf` **не була причиною** пошкодження — вона лише стала тригером який виявив приховану проблему диска. Сайт міг впасти в будь-який інший момент при будь-якій активній операції з файлами.
